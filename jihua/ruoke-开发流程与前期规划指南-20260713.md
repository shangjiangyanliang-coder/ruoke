# 若可(Ruoke)学习辅助App - 前期规划与开发流程指南

> 项目名称（暂定）：若可 Ruoke —— 笔记 + 题库 + AI 辅助学习 App
> 技术路线（已定）：方案 A —— Flutter 跨平台手机 App（语言 Dart）
> 编写日期：2026/07/13
> 面向对象：项目主导人（编程小白）
> 文档目的：在动手写代码之前，先讲清楚"一个软件项目从想法到上线"应走的完整流程，让前期规划与规范工作合理、高效、安全。

---

## 第〇部分 写在前面：你必须先建立的几个认知

在你还是编程小白、且独自推动一个含 AI 功能的 App 项目时，有几条认知比任何技术细节都重要，请先记住：

1. **软件项目 = 工程问题，不是天才问题。** 真正决定成败的不是你用了多牛的技术，而是"需求清不清楚、流程规不规范、能不能持续收尾"。技术栈可以换，方向跑偏了代价才大。
2. **不要一上来就写代码。** 小白最大的风险是"凭感觉敲代码"，三天后看不懂自己写的、一周后改不动、一个月后放弃。先规划，再动手。
3. **小步快跑、先做 MVP（最小可用版本）。** 一次性想做笔记 + 题库 + AI 大海滔滔，必然烂尾。先做一个有 1 个核心功能、能真正用起来的最小版本。
4. **文挡和备份比代码更重要。** 需求文档、设计决定、踩坑记录，这些"非代码产物"才是项目能持续下去的命根子。
5. **AI 是你的"工程师副驾"，不是替你做决定的人。** 你是产品负责人 + 测试员 + 决策者；AI 帮你写代码、查资料、解释概念；但"做什么、不做什么、做到什么程度"由你拍板。

## 第一部分 一个软件项目的完整生命周期（SDLC）

不管你用什么技术，正规项目都会经历这几个阶段。下面我按"阶段 → 你要做什么 → 产出什么文档"来讲。

### 阶段 1：需求分析（Idea → 明确"做什么"）

**目的**：把脑子里模糊的"我想做个学习 App"变成清晰的、可执行的功能清单。

**你要做的事**：
- 问自己：这个 App 给谁用？（自己用 / 朋友用 / 公开发布？）—— 这决定了你做到多严谨。
- 把"想法"拆成一个个具体功能。比如"AI 辅助"太虚，要拆成"AI 生成闪卡""AI 解答错题""AI 总结笔记"等。
- 区分"必须有"和"有了更好"。MVP 只做必须有。
- 想清楚每个功能的**输入是什么、输出是什么、用户怎么操作**。

**产出文档**：
- 《产品需求文档 PRD》：功能清单 + 每个功能的描述 + 优先级
- 《用户故事》：用"作为……我想……以便……"的句式描述每个需求
- 一份简单的脑图或功能树

**小白提醒**：这一步不要怕花时间。需求清楚，后面少返工 70%。

---

### 阶段 2：产品与交互设计（明确"长什么样、怎么用"）

**目的**：把文字需求变成"屏幕长什么样、点哪里去哪里"。

**你要做的事**：
- 画**线框图**（草图级别即可）：每张关键页面长什么样、按钮在哪。
- 画**页面流程图**：从首页点到笔记页、点到题库页的跳转关系。
- 不需要很精美，能把"哪个页面有哪些东西、点完去哪"讲清楚就行。

**产出文档**：
- 线框图 / 页面草图（可手绘拍照、可用免费工具如 Figma）
- 页面流程图（可用纸笔或免费画图工具）

**工具推荐**：纸笔最快；想数字化用 **Figma**（免费）或 **Excalidraw**（免费、手绘风、适合画流程）。

---

### 阶段 3：技术方案设计（明确"用什么技术搭"）

**目的**：决定用什么编程语言、什么框架、什么数据库、怎么部署。这是对小白最关键、也最容易踩坑的一步。

**你要做的事**：见下面"第二部分 技术选型"，我把笔记+题库+AI 这类项目的选型专门帮你拆出来讲。

**产出文档**：
- 《技术方案文档》：技术栈选择 + 每个选择的理由 + 备选方案对比
- 《架构草图》：前端在哪、后端在哪、数据库在哪、AI 接口怎么调（一张简图即可）

---

### 阶段 4：项目骨架与规范搭建（动手前的最后准备）

**目的**：在写第一行业务代码前，先搭好"项目骨架"和"开发规范"，避免后续混乱。

**你要做的事**：
- 初始化项目目录结构（前端代码、后端代码、文档各放哪）
- 初始化 **Git 版本仓库**（记住：没有 Git 的项目等于没有存档，电脑坏一次全完）
- 约定代码规范：文件命名、代码注释、提交信息怎么写
- 约定备份与目录规范（你已有 jihua/beifen/ceshi 的习惯，继续保持）

**关键概念解释**：
- **Git**：代码的"存档系统"。每次改完代码"存一个档（commit）"，出问题能"读档回退"。这是项目安全的第一道保险。可托管在 GitHub/Gitee 上。

**产出文档**：
- 初始化好的项目目录 + Git 仓库
- 《开发规范文档》：命名规则、注释规则、提交信息规则

---

### 阶段 5：编码开发（真正写代码）

**目的**：按需求逐个实现功能，并随时能跑起来看效果。

**你要做的事**：
- 按功能优先级，一次只做 1~2 个功能，做完能运行再说下一个。
- 每做完一个小功能就"存档（git commit）"。
- 边写边测：每个功能做完自己在 App 里点一遍看对不对。

**产出文档 / 产物**：
- 可运行的代码
- 每个功能的简单说明

**小白提醒**：
- 一次只啃一个小功能，别贪多。
- 看不懂报错就把报错贴给 AI，让它解释 + 给修法。

---

### 阶段 6：测试（确认"能用且不出错"）

**目的**：保证功能真的正常，别"在我电脑上能跑、到你那就崩"。

**你要做的事**：
- **手动测试**：自己照"用户故事"把每个功能点一遍。
- 关键功能（数据保存、AI 调用）做几组**边界测试**：空内容、超长内容、断网情况。
- （进阶）写自动化测试：小白阶段可先以手动为主，后期再补。

**产出文档**：
- 《测试清单》：每个功能 → 预期结果 → 实测通过/不通过

---

### 阶段 7：部署上线（让别人能用）

**目的**：让 App 从"我电脑上能跑"变成"别人能下载/访问"。

**你要做的事**：
- 移动 App（手机）→ 生成安装包，发布到应用商店或自留安装包
- 网页版 → 部署到云服务器或静态托管平台
- 后端 API → 部署到云服务器或 Serverless 平台

**小白友好路线**：
- 网页可先白嫖免费托管：Vercel / Netlify / GitHub Pages
- 后端最小可用：可用 Cloudflare Workers（有免费额度）或轻量服务器

**产出文档**：
- 《部署说明》：怎么打包、怎么发布、在哪里访问

---

### 阶段 8：维护与迭代（上线只是开始）

**目的**：修 bug、加功能、随用户反馈持续改进。

**你要做的事**：
- 记录用户反馈 / 自己 bug（放进 jihua 或专门一个 issues 文件）
- 定期备份
- 按优先级迭代下一版

## 第二部分 技术选型（针对你的"笔记+题库+AI"App）

这部分是给小白最该认真看的。选型错了，越往后越痛苦。下面给你几套**对你这种背景相对友好**的方案，并说明利弊。

### 方案 A：纯跨平台 App 路线（Flutter）

**是什么**：用一套代码同时生成 Android 和 iOS 两个平台的手机 App。语言是 Dart。

**优点**：
- 一套代码两端通吃，量小力大
- 界面美观，动画顺滑，适合"笔记"这类内容型 App
- AI 调用走 HTTP 即可，集成成熟

**缺点**：
- Dart 对完全没编程基础的人有一定学习成本
- 要分别配 Android、iOS 的构建环境
- iOS 发布需要苹果开发者账号（收费）

**适合**：你最终一定要"手机原生 App"、且不在乎学一门新语言。

---

### 方案 B：网页应用 + 渐进式路线（推荐给纯小白起步）

**是什么**：做成网页，手机浏览器直接打开就能用。后期可加壳打包成 App。

技术栈建议：
- 前端：**React**（最主流、资料最多、AI 最熟）+ **Vite**（构建工具，快）
- 后端：**Node.js + Express**（最少配置）或 Serverless 函数
- 数据库：先 **SQLite**（单文件、零配置、本地即可跑），用户多了再上 PostgreSQL

**优点**：
- 上手资料最多，AI 写这个最在行，遇到问题最容易搜到答案
- 不用配手机构建环境，浏览器打开就能看
- 数据库存本地 SQLite 一条命令就能用
- 后期若要打包手机 App，可用 Capacitor 等工具加壳

**缺点**：
- 不是严格意义上的"手机 App"，离线、推送等原生能力弱一些
- 你若是"非网页不用、必须手机桌面图标"，需要额外加壳步骤

**适合**：纯小白起步、想快速看到成果、先证明想法可行。

---

### 方案 C：Expo + React Native（原手机 App，又尽量简单）

**是什么**：用 React 写手机 App，配 Expo 工具链免去大量原生配置。

**优点**：体验是真手机 App；Expo 让构建/预览更省事；前端用 React。
**缺点**：比纯网页复杂；部分原生功能受 Expo 限制；仍有上架费（iOS）。
**适合**：你确定要真手机 App，又想比方案 A 更贴近 Web 思路。

---

### AI 能力怎么接（不分方案，通用思路）

- AI 模型接口放**后端**，不要把 API Key 写在前端（否则任何人能从 App 里偷走你的密钥）。
- 前端只发"用户问的内容"到后端，后端带着密钥去问 AI，再把答案返回前端。
- 模型选择：可先用主流商用 API（调用简单、效果好、按量付费）。

---

### 我的建议（你可以选）

| 你的侧重点 | 推荐路线 |
|---|---|
| 想最快看到能用的东西、验证想法 | 方案 B（网页起步） |
| 一定最终是手机 App、愿意学新语言 | 方案 A（Flutter） |
| 一定手机 App、又想延续 Web 思路 | 方案 C（Expo+RN） |

我个人作为助手会建议你：**先用方案 B 起步做 MVP**，理由是"零门槛看到成果、配环境最少、出问题最好查、AI 帮你写最在行"。等想法验证、你也摸熟了开发节奏，再决定要不要重做成原生 App 或加壳。这条"先简易后正规"的路，是小白不烂尾的最稳打法。

## 第三部分 项目安全与质量规范（你要坚持的几条底线）

这部分是你 CLAUDE.md 里"安全开发模式"在项目层面的延续，建议作为团队（哪怕只有你 + AI）长期守则：

### 1. 版本管理（Git）红线
- 每天至少一次"上传代码到远程仓库（GitHub/Gitee）"，等于云端备份。
- 改功能前先切一个新分支，改完合并。
- 永远别直接覆盖主干（main）。

### 2. 密钥与敏感信息
- API Key、Token、数据库密码绝不写进代码，统一放 `.env`，且 `.env` 不上传 Git（加入 .gitignore）。
- 若不小心提交了，立即撤销 + 更换密钥。

### 3. 备份与"安全网"习惯
- 你已有的 jihua/beifen/ceshi 三件套继续保持：计划进 jihua、改文件前进 beifen、临时测试进 ceshi。
- 重要代码也进 Git 双保险。

### 4. 不可逆操作前确认
- 删文件、重置 Git、推发布、输入真密钥——这些动作 AI 必须先问你，不得自作主张。

### 5. 功能边界与数据保护
- 笔记/题库 AI 自动生成内容时，要保留"用户可修改"的能力，不能让 AI 不可撤销地覆盖用户笔记。
- 重要的笔记数据，留好"恢复/历史版本"的可能（哪怕先简单记录）。

## 第五部分 小白特别提醒

- **别指望一次定终身**。规划可以改，发现想错就回来改文档，这是正常的。
- **遇到不懂就问 AI**：让 AI 解释报错、解释术语、对比方案。但决策归你。
- **警惕"过度设计"**：MVP 阶段不要上微服务、不要上复杂架构，能用简单方案就简单。
- **保留全部过程文档**：你为什么这么选、踩了什么坑，都记下来。半年后回看不至于断片。
- **每周给项目拍一次快照**（git push + 备份关键文档），这是防烂尾的安全网。

## 第六部分 Flutter 路线详解（方案 A 专用）

你已选方案 A：用 Flutter 写手机 App。下面把这条路线从"环境搭建→架构→目录→上线"讲清楚，供你照着走。

### 6.1 Flutter 是什么 / 它的分工

- **Flutter**：Google 出的"界面框架"，你写一套 Dart 代码，它帮你同时生成安卓和 iOS 两个平台的手机 App，界面统一好看。
- **Dart**：Flutter 用的编程语言，语法风格接近 Java/JS，不难。
- **包管理工具**：Flutter 自带 `pub`，类似"零件超市"，你需要什么功能（数据库、网络、图标等）去 `pub.dev` 拿，写进 `pubspec.yaml`。

### 6.2 开发环境搭建（你要装的软件清单）

按顺序装（具体命令我们到时一起执行，这里先列清楚）：

| 软件 | 作用 | 是否必需 |
|---|---|---|
| **Flutter SDK** | Flutter 开发套件本体 | 必需 |
| **Android Studio** | 提供安卓模拟器 + 安卓编译环境 | 必需（安卓） |
| **VS Code** | 写代码的编辑器，装 Flutter/Dart 扩展 | 强烈推荐 |
| **Git** | 代码存档 | 必需 |
| iOS 构建环境（Xcode） | 只在 macOS 上 | 你要发 iOS 才需要 |

**小白起步建议**：先用 **安卓模拟器**（Windows 电脑就能跑）开发调通，iOS 等以后有 Mac 再说。这样起步成本最低。

### 6.3 Flutter 官方推荐架构：MVVM + 分层（这是你要照搬的骨架）

官方把 App 分成两大层（外加可选的 Domain 层），核心是"关注点分离"——每一层只管自己的事：

```
┌──── UI 层 ────┐
│  View  ⇄  ViewModel │   View=页面看着(W); ViewModel=管这个页面的状态和逻辑
└──────────┬─────────┘
           ↓ 取数据
┌──── Data 层 ──┐
│ Repository ⇄ Service │  Repository="数据总入口/唯一真相源"; Service=对接外部(API/数据库/文件)
└────────────────────┘
   （可选 Domain 层：放复杂业务用例 UseCase，MVP 阶段先不建）
```

一句话记法：
- **View**：决定"页面长啥样"，不含业务逻辑。
- **ViewModel**：决定"这个页面该显示什么数据、点了按钮干嘛"。
- **Repository**：决定"数据从哪来、怎么缓存"，是所有数据的唯一入口。
- **Service**：负责真去访问外面（网络、数据库文件）。
- 规则：**View 不直接碰 Repository，数据流永远 ViewModel → Repository → Service**。

### 6.4 推荐技术栈清单（MVP 阶段够用、不过度设计）

| 用途 | 推荐选型 | 一句话说明 |
|---|---|---|
| 框架 | Flutter | 一套代码出两端 |
| 语言 | Dart | Flutter 唯一语言 |
| 状态管理（管界面数据怎么变） | **Riverpod** | 官方文档主推，小白也能从简单用法开始 |
| 本地数据库（存笔记/题库） | **Drift**（基于 SQLite） | 带"型号检查"的数据库库，比裸 SQLite 少踩坑、对小白更友好 |
| 远程接口请求 | **dio** | 调后端/AI 接口用，比官方自带更顺手 |
| 路由（页面跳转） | **go_router** | 官方推荐，管理"从 A 页跳 B 页" |
| 依赖注入（管对象怎么传） | **Riverpod** 自带 | 同一个工具复用，少学一个 |
| 密钥管理 | **flutter_dotenv** | 读 `.env` 文件里的密钥，不写死在代码 |
| 持久化设置 | **shared_preferences** | 存"主题/字号"这类小配置 |

> 名词小释：**状态管理**就是"界面上的数据变了，怎么自动刷新显示"。Riverpod 是当前主流做法。

### 6.5 推荐目录结构（feature-first，按功能分文件夹）

```
ruoke_app/
├── lib/                    ← 你的代码都在这
│   ├── main.dart           ← 程序入口
│   ├── src/
│   │   ├── features/       ← 按功能分（每个功能一个文件夹）
│   │   │   ├── notes/      ← 笔记功能
│   │   │   │   ├── view/   ← 页面（View）
│   │   │   │   ├── view_model/ ← 状态逻辑（ViewModel）
│   │   │   │   ├── repository/ ← 数据入口
│   │   │   │   └── models/  ← 这个功能的数据结构
│   │   │   ├── quiz/       ← 题库功能（同上分法）
│   │   │   └── ai_assist/  ← AI 辅助功能
│   │   ├── data/           ← 跨功能共享的数据层（数据库、AI 接口 Service）
│   │   ├── routing/        ← 页面跳转配置
│   │   ├── themes/         ← 主题/颜色/字号
│   │   └── utils/          ← 通用小工具
├── assets/                 ← 图片、字体等静态资源
├── test/                   ← 测试代码
├── pubspec.yaml            ← "零件清单"：列你要用的包
├── .gitignore              ← 告诉 Git 哪些别上传
└── .env                    ← 密钥放这（绝不上传 Git）
```

**记忆口诀**：一个功能 = `view`(页面) + `view_model`(逻辑) + `repository`(数据) 一套，自己关起门来管自己。

### 6.6 .gitignore 必须忽略的（防止泄密和上传垃圾）

作为 Flutter 项目，这些绝不能上传：`.env`、`build/`、`.dart_tool/`、`.flutter-plugins`、各平台构建产物。这些到时配项目时一起写好。

### 6.7 上线发布概览（以后用，先有个概念）

- **安卓**：`flutter build appbundle` 生成 `.aab`，传 Google Play；或 `flutter build apk` 出安装包自留分发。

## 第七部分 开发规范（项目长期守则）

下面这些规范请作为"团队守则"（哪怕只有你 + AI），从第一行代码就坚持，能省掉后面 80% 的混乱。

### 7.1 命名规范（文件、变量、函数）

- **文件名**：全小写 + 下划线，如 `note_editor_view.dart`、`quiz_repository.dart`。
- **类名**：大驼峰，如 `NoteViewModel`、`QuizRepository`。
- **变量/函数名**：小驼峰，如 `loadNotes()`、`currentNote`。
- **常量**：全大写 + 下划线，如 `MAX_NOTE_LENGTH`。
- **私有**：以 `_` 开头表示"只在本文件内用"，如 `_database`。
- **功能文件夹名**：业务用英文（`notes`/`quiz`），文档用中文也行。

### 7.2 代码注释规范

- **文件头**：每个文件顶上写 1 行说明这文件是干嘛的、属于哪个功能。
- **函数**：复杂函数（>20 行或有逻辑判断）在上方写 2~3 行注释：做什么、入参、返回。
- **避坑点**：在"为什么这么写"的地方留注释（不是"写了什么"，而是"为什么"）。
- **TODO**：临时没做完、待优化的地方写 `// TODO: 说明`，便于全项目搜索回头补。

### 7.3 提交信息规范（Git commit message）

统一格式 `类型: 简述`：

| 类型 | 含义 | 例子 |
|---|---|---|
| `feat` | 新功能 | `feat: 新增笔记编辑页` |
| `fix` | 修 bug | `fix: 题库空内容崩溃问题` |
| `docs` | 改文档 | `docs: 补充需求清单` |
| `refactor` | 重构（不改功能） | `refactor: 拆分笔记 ViewModel` |
| `chore` | 杂项（配置/依赖） | `chore: 升级 drift 依赖` |
| `style` | 只改格式 | `style: 统一缩进` |
| `test` | 加/改测试 | `test: 笔记保存测试` |

一次提交只做一件事。别"一个 commit 改了三个功能"。

### 7.4 分支规范（Git 工作流）

- `main`：稳定主干，永远可直接打包能跑的版本。
- `dev`：开发主线，新功能在这合并。
- `feature/xxx`：每做一个功能切一个分支，做完合并回 `dev`。
- `fix/xxx`：修 bug 专门分支。
- 规则：**不直接往 main 写代码**，都走分支再合并。小白阶段可简化到 main + 功能分支两支即可。

### 7.5 密钥与安全规范

- 所有 API Key、Token、密码**一律**放 `.env`，代码里只读取不写死。
- `.env` 加入 `.gitignore`，永不进 Git。
- 仓库里放一份 `.env.example`（只有名字没真值），告诉后来者要填哪些。
- 一旦发现密钥误传，**立即在平台作废重发 + 用 git 历史清除**，不能只删当前版本。

### 7.6 AI 调用安全规范（你项目特别重要）

- AI 调用必须放**后端**层，密钥绝不进 App 前端代码（反编译就能偷走）。
- 小白阶段若没后端：可先用一个最简后端（如轻量云函数）代理 AI 请求；纯本地调试可临时放 `.env`，但**上线前必须移到后端**。
- AI 生成内容默认**不覆盖**用户数据：要么生成到新草稿、要么需要用户点"应用"才生效。
- 给 AI 的内容做"敏感词过滤"意识：别把用户隐私笔记整段丢给公共模型 API（先告知用户、或提供开关）。

### 7.7 目录与备份规范（延续你的 jihua/beifen/ceshi 三件套）

- `jihua/`：存阶段计划、需求文档、设计决定、规范文档（本文件就在这）。
- `beifen/`：每次改文件前，把原文件复制一份进来再改（原文件名+备份）。
- `ceshi/`：临时测试文件放这；用完能删的，在文件名前加`删除`二字，待你确认后删。
- 代码层面：额外靠 **Git** 做第二重保险。

### 7.8 每日/每周节奏（防烂尾的科学节奏）

- **每次开工**：先 `git pull` 拉最新，再切功能分支。
- **每做完一个小功能**：自测能跑 → `git commit` → 推到远程。
- **每天结束**：保证当天改动已 commit + push 到远程（云端快照）。
- **每周**：备份一次关键文档到 `beifen/`，回顾这周做了啥、下周做啥，记进 `jihua/` 的周记。

### 7.9 测试规范（小白阶段起步版）

- MVP 阶段以**手动测试**为主：每个功能做完，照"用户故事"点一遍。
- 关键功能强测：数据保存（增删改）、AI 调用（联网/断网）、空数据/超长数据。
- 写下《测试清单》放 `jihua/`：功能名 → 预期结果 → 实测 ✓/✗。
- 后期再逐步引入 Flutter 的 `test/` 自动测试（先从最核心的数据层开始写）。
