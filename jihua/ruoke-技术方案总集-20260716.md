## 二、分层架构（MVVM + Repository）

### 2.1 四层 + 一域
```
┌──────────────────── UI 层 ────────────────────┐
│  View (Widget)  ⇄  ViewModel (Notifier)       │  View=页面长啥样;ViewModel=该页状态与逻辑
└──────────────────────┬────────────────────────┘
                       ↓ 只依赖接口/不直接碰数据源
┌──────────────────── Domain 层(可选) ──────────┐
│  UseCase (复杂跨 Repository 业务用例)           │  MVP 阶段先不建,简单逻辑直接在 ViewModel
└──────────────────────┬────────────────────────┘
                       ↓
┌──────────────────── Data 层 ──────────────────┐
│  Repository(接口) ⇄ LocalRepository(Drift实现) │  Repository=数据唯一入口/真相源
│                 ⇄ Service(OS/网络/文件/OCR)     │  Service=对接外部(相机/文件/AI/OCR)
└───────────────────────────────────────────────┘
```

### 2.2 各层职责与红线
| 层 | 职责 | 红线（不准做） |
|---|---|---|
| View (Widget) | 画页面、把 ViewModel 状态渲染出来、把点击事件转成 ViewModel 方法调用 | ❌ 不直接调 Repository / ❌ 不写业务判断 / ❌ 不存可变状态 |
| ViewModel (Notifier) | 管本页状态、调 Repository 拿数据、把结果放进 state 通知 UI 刷新 | ❌ 不 import Drift / ❌ 不直接调 dio / ❌ 不知道 UI 细节 |
| Repository (接口) | 对外暴露数据读写方法（如 `listNotes`/`createNote`）；屏蔽"数据从哪来" | ❌ 不写 Widget / ❌ 不持有 UI 状态 |
| LocalRepository (实现) | 用 Drift 真去读写 SQLite；变 JSON/派生 plain_text/触发 version 快照/软删 | ❌ 不被 ViewModel 直接 new（走 Riverpod 注入） |
| Service | 对接外部：相机/相册、文件、AI API(dio)、本地 OCR、对象存储(V2) | 被 Repository 调用，不直接被 ViewModel 调用（AI 调用经 Repository 封装） |

### 2.3 数据流向（单向，必须照走）
```
用户点击 → View → ViewModel 方法 → Repository → (LocalRepository or Service)
       ← state 变 ← Riverpod 通知 ← 数据返回 ←
```
- **View 不碰 Repository**：数据流永远 `View → ViewModel → Repository → Service`。
- **Repository 是唯一真相源**：ViewModel 不知道数据是在 SQLite 还是云（决策9 预留口），只调 Repository。
- **AI 调用经 Repository**：ViewModel 不直接发 dio，经 AiRepository 封装（便于挂隐私过滤、不可用兜底、模型自选）。

### 2.4 域层 Domain 何时引入
MVP 阶段不建 UseCase 层。出现以下信号才抽 UseCase（V2 候选）：
- 一个动作要协调 ≥3 个 Repository（如"重点转题并入库并建复习卡"跨 Notebook/Quiz/Review）。
- 同一段业务逻辑被多个 ViewModel 复用。
届时抽一个 `domain/usecases/xxx_usecase.dart`，ViewModel 调它。MVP 先把这些逻辑写在对应 ViewModel 里，足够清楚就不硬拆。

## 四、Riverpod Provider 划分原则（小白能照搬的范式）

### 4.1 四种 Provider 何时用
| 类型 | 何时用 | 官方小贴士 |
|---|---|---|
| `Provider` | 只读一个不变值/一个对象（如数据库单例、路由配置） | 简单依赖 |
| `FutureProvider` | 一次性异步取值（如"首次加载笔记列表"），自带 loading/error 状态 | 只读异步结果 |
| `StreamProvider` | 监听持续更新（如 Drift 的 `watch()` 流查询，表变 UI 自动刷） | 列表/详情响应式 |
| `NotifierProvider` (推荐 `AsyncNotifierProvider`) | 有可变状态 + 方法的页面状态机（ViewModel 本体） | 90% 页面的 ViewModel 用这个 |

### 4.2 一个页面一套 ViewModel 范式（照抄）
```dart
// view_model/note_list_view_model.dart
@riverpod                  // 用 riverpod_generator 生成(推荐,少写样板)
class NoteListVm extends _$NoteListVm {
  @override
  Future<List<Note>> build() {
    // 进入页面即拉数据,走 Repository(经 ref.read 拿 Repository Provider)
    return ref.read(noteRepositoryProvider).listBySubject(currentSubjectId);
  }

  Future<void> createDraft() async {
    final id = await ref.read(noteRepositoryProvider).create(/*draft*/);
    state = AsyncData([...?state.valueOrNull, /*new*/]);
  }

  Future<void> softDelete(String noteId) async {
    await ref.read(noteRepositoryProvider).softDelete(noteId);
    state = AsyncData(state.valueOrNull?.where((n) => n.id != noteId).toList() ?? []);
  }
}

// view/note_list_view.dart
class NoteListView extends ConsumerWidget {
  Widget build(context, ref) {
    final list = ref.watch(noteListVmProvider);
    // 跟随自动刷:仅 UI 看FutureProvider决定了
    ...
  }
}
```

### 4.3 划分原则
1. **一页一 ViewModel**：一个页面要变的状态放一个 AsyncNotifier；跨页共享极少的才独立成 Provider。
2. **Repository 是 Provider 单例**：`noteRepositoryProvider` 全局一个，Pointer 内由 Riverpod 注入，ViewModel 用 `ref.read(noteRepositoryProvider)` 调用。
3. **数据响应式**：列表/详情用 Drift 的 `watch(stream)` + `StreamProvider` 替代手动刷新，表一变页面自动刷（Drift 强项）。
4. **不在 Widget 里 `ref.read` 改状态**：所有改状态的动作走 ViewModel 方法；Widget 里 `ref.watch` 只读、事件 handler 调 vm 方法。
5. **dispose 自动**：Riverpod 自动管生命周期，小白不用手动 dispose；离开页面即回收。

### 4.4 是否用 riverpod_generator
推荐用 `riverpod_generator` 包（`@riverpod` 注解生成），少写样板、名字不冲突。小白可先从手写 `NotifierProvider` 起步熟悉再上 generator。MVP 阶段建议直接上 generator，文风统一。

## 六、错误处理与日志统一

### 6.1 统一异常（data/errors/）
- 定义项目异常基类 `AppException`，子类：`DataBaseException` / `NetworkException` / `AIServiceException`(含"不可用"/"模型未配"/"联网失败"三种) / `OcrException` / `ValidationException`。
- AI 不可用三种状态映射为枚举 `AiAvailability { ok, notConfigured, offline, disabledByPrivacy }`，供 C19 灰显判断。

### 6.2 Repository 统一 try-catch + Result 包装
- Repository 方法返回 `Future<Result<T>>`（Result = Success(data) / Failure(AppException)），把底层异常翻译成领域异常，不让 SQL/dio 异常泄漏到 ViewModel。
- ViewModel 拿到 Failure → 决定"显 UI 提示" or "记日志 + 重试"。

### 6.3 用户可见提示风格
- 一般失败：底部 SnackBar 一行话（通俗，无堆栈）。
- AI 不可用：对应 C19 灰显 Banner + 一行说明 + 退路按钮（见 C 文档）。
- 数据校验失败：对应输入框下红字提示（如 D2 题空存时保存置灰 + 提示）。
- 绝不把堆栈/技术错误抛给用户。

### 6.4 日志策略
- 开发期：用 `debugPrint` 打结构化日志（tag + 消息），不上生产。
- 引入轻量日志（可选 `logging` 包或自写 `AppLogger`），统一 `i/w/e` 三级，dev 打全量、release 只打 error。
- **不记任何用户笔记内容/AI 对话明文到日志**（隐私，呼应待细化7）。

## 一、设计总原则（折中方案）

经"多建独立表 vs 塞 JSON"权衡，本项目取**折中**策略：

1. **核心实体建独立表**（科目/笔记/题/复习卡/错题/做题记录/识图素材/AI 会话/标签等）——这些要查询、统计、跨功能关联，必须独立表，享受 SQL 的高效查询、外键约束、聚合统计。
2. **明细存 JSON 列**（题的选项、笔记正文、AI 对话逐条消息、复习卡的 SM-2 状态块、题的解析）——这些"跟着主行一起读写、不单独被查"的塞 JSON，省表又不影响统计。
3. **N 对 N 关联用独立关联表**（note_tag 笔记-标签、quiz_question_error_cause 题-错因）——关联必须独立表，塞 JSON 查不动。
4. **daily_plan 不建表、纯算**：C6 每日清单由"复习卡到期日 + 错题未做 + 笔记草稿态 + 识图未处理"实时计算；"今日已学"留痕走 quiz_attempt / review_card 的完成时间戳反推，不另存。
5. **所有表主键用 UUID（字符串）**：本地无账号，UUID 天然唯一、跨设备不冲突，将来上多用户时只需加一列 userId，不破坏既有结构（待细化9/10 已定）。
6. **所有表带 createdAt / updatedAt 时间戳**：上云同步比对版本用（待细化9），即使 MVP 不上云也先存好，避免后期补字段迁移痛苦。
7. **软删除 + MVP 即做回收站可恢复**：重要实体（笔记/题/科目/标签/识图素材等）带 `isDeleted` + `deletedAt` 标志，删了不真丢、进回收站可恢复（F3.30）；MVP 即实现回收站 UI 与恢复逻辑（用户已定"回收站可恢复"），不推迟到 V2。错题"移出本本"不真删题、只置 resolved=true 软移除。删除 = 置 isDeleted=true + deletedAt=now；恢复 = 置回 false + deletedAt=null。
8. **字段命名**：Drift 在 Dart 端用小驼峰（contentJson），数据库列名用小写下划线（content_json），Drift 自动转换，文档以数据库列名描述。

## 五、Repository 接口约定（本地优先 + 上云预留口）

### 5.1 分层原则
- **ViewModel 只认 Repository 接口**，不碰 Drift / 不碰网络。
- **Repository 接口落在 domain/data 层**，MVP 实现是 `LocalXxxRepository`（Drift），未来加 `RemoteXxxRepository`（云端）走同一接口、配置切换。
- **每个功能块一个 Repository**：NoteRepository / QuizRepository / ReviewRepository / StudyRepository / OcrRepository / AiRepository / BackupRepository / SettingRepository。

### 5.2 上云预留口（待细化9 已定："Repository 标本地/远程可换、上云只在用户主动备份/恢复触发"）
- 所有 Repository 接口方法以"读/写本地"为主干。
- 额外定义两个方法挂在 **BackupRepository**（不是每个业务 Repository 都加同步）：
  - `Future<void> backupToCloud()` —— 用户主动点"备份到云"才调，把加密包推到对象存储（远期）
  - `Future<void> restoreFromCloud()` —— 用户主动点"从云恢复"才拉
- MVP 不实现 cloud，接口先空抛 `UnimplementedError`，保证调用点就位、将来填实现不动上层。
- **无后台自动同步**（决策已定），Repository 不设自动定时同步。

### 5.3 接口示例（伪 Dart，写法待技术方案 A 再定签名风格）

## 四、SM-2 复习算法

### 4.1 算法实现要点
- 标准 SM-2：质量分 q(0-5) → 重算 ease_factor(EF)、interval、repetitions、next due。
- 自评 1-5（C7 五档表情）→ q 映射：
  - 1 完全忘 → q=0
  - 2 挣扎 → q=2
  - 3 回想 → q=3
  - 4 记得 → q=4
  - 5 熟透 → q=5
- "不评/再看一遍"（C7 约定）→ **不调算法**，due_at 不变（不默变好变差）。
- q<3 → repetitions 归 0（重学），interval 回 1 天；q>=3 → 正常推进。
- EF = max(1.3, EF + (0.1 - (5-q)*(0.08 + (5-q)*0.02)))（标准公式）。
- 首次 interval=1，二次=6，之后 round(interval*EF)。

### 4.2 统一接口（V2 升 FSRS 平滑替换）
```dart
abstract class ReviewScheduler {
  ReviewState schedule(ReviewState current, int quality);  // 重算状态
  DateTime nextDueAt(ReviewState state, {DateTime now});
}
class SmTwoScheduler implements ReviewScheduler { ... }      // MVP
class FsrsScheduler implements ReviewScheduler { ... }       // V2
```
- review_card 存的字段（interval/ease/repetitions/due_at）是 SM-2 的；FSRS 接入时若需新字段，加列迁移 + scheduler 实现解析，**Repository/ViewModel 不变**（决策⑥ 统一接口）。

### 4.3 数据落点
- C7 翻卡自评 → `ReviewRepository.review(cardId, quality)` → scheduler 算 → 更新 review_card。
- 复习卡来源：题（quiz_question）或重点（note_highlight），target_type 区分。
- C6 每日"待复习"= `review_card.due_at <= today 且未软删`。

- d2) q<3 归零重学、首日间隔 1/6 天 —— 接受标准 SM-2 还是想调？
