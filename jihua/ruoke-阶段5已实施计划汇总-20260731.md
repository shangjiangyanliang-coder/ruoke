## 一、阶段5总体目标

阶段5以笔记模块为主线，建立可复用的本地数据底座，并逐步形成以下闭环：

1. 笔记新建、编辑、保存、删除；
2. Flutter Quill 富文本编辑；
3. 书—章—节分级和笔记归属；
4. 红字、下划线重点提取；
5. 历史版本、恢复和版本管理；
6. 标签输入、标签搜索和笔记搜索；
7. 文件夹—书—章—节—笔记的目录浏览；
8. 从当前位置逐层选择新建内容和笔记归属。

统一技术路线：

- Flutter 3.44.4、Dart 3.12.2；
- feature-first + View → ViewModel → Repository → DAO；
- Riverpod 手写 Provider/AsyncNotifier；
- Drift + SQLite 本地数据库；
- GoRouter 页面导航；
- 所有功能按 Red → Green → Refactor 实施；
- 不在未经确认时 push，不直接删除备份。

## 三、已实施批次设计决策归档

> 本章由此前 7 份独立设计文档合并而来，只归档已经实施批次的关键决策、方案取舍和边界。各批次的实际交付与验证仍以第二章时间线为准。

### 1. 编辑器稳定性与标签搜索基础设计

#### 编辑器稳定性

- 空笔记必须同时满足标题 trim 后为空、Quill 纯文本去除自动结尾换行和其他空白后为空；只有标题或只有正文都属于有效笔记。
- 新空笔记保存时不调用 Repository；退出时选择保存也只跳过创建，不产生空记录。
- 保存结果必须区分 `saved`、`skippedEmpty`、`failed`，避免把数据库失败误报为空笔记。
- 新建编辑器以当前 `noteId/subjectId` 建立独立初始化会话，路由参数变化时释放旧 Controller；不使用固定延时掩盖竞态。
- F1.1.14 只有在首次新建、首次打开、旧笔记后立即新建、连续进出和初始化失败场景均不再永久转圈后才关闭。

选择该方案是因为它只隔离编辑会话和保存语义，不需要重构整个编辑器架构，同时能阻止空数据污染搜索与标签统计。

#### 标签与搜索基础

- 标签采用独立 `TagRepository`，删除标签和清理 `note_tag` 在同一事务内完成，不删除笔记。
- 多标签筛选采用并集；关键词、标签和后续范围条件之间采用交集。
- 搜索字段为标题和 `plain_text`，基础实现使用 SQLite `LIKE`，不引入全文索引、拼音搜索、模糊纠错或分页。
- 标签只作为书—章—节分级的辅助组织方式，目录树始终是笔记主视图。

### 2. 标签自由输入与搜索会话设计

原先“先在管理页创建标签，再到编辑器引用”的流程被否决，因为会割裂编辑过程。最终改为：

- 编辑器直接输入任意标签；完全同名时复用，不存在时在保存事务中创建。
- 新笔记无真实 noteId 时，标签只存在当前编辑会话；空笔记不能因标签操作创建笔记或标签。
- 标签名称和标题/正文都支持 `contains` 与 `exact` 两种匹配模式。
- `SubjectScope` 统一表达全部、指定书/章/节子树及全部书/章/节直接归属范围。
- 指定书包含书及其章、节；指定章包含章及其节；指定节只含自身。
- 标签搜索与通用搜索使用独立、自动释放的 Provider 会话；退出重进统一恢复空关键词、无标签、部分匹配、全部笔记和最近更新。
- ViewModel 使用请求修订号，较慢旧查询不得覆盖新条件；页面销毁后的结果不得写入新会话。

没有采用单一全局搜索状态，因为它会让标签入口和通用搜索互相污染，并导致重新进入后残留上次关键词。

### 3. 真机反馈改造：标签草稿、完整快照与范围树

#### 标签草稿和原子保存

- 已有笔记添加、移除标签只修改 `NoteEditorVm` 内存草稿，不即时写入数据库。
- 标题、正文、标签任一变化都触发统一 dirty 判断和退出确认。
- 保存时在同一个 Drift 事务中完成旧快照、note、重点、tag 和 `note_tag`；任一步失败全部回滚并保留编辑器草稿。
- 仅有标签、没有标题和可见正文的新笔记仍属于空笔记，不创建任何持久化数据。

#### 完整历史快照

- 新格式 `NoteEditSnapshot` 保存 `schemaVersion`、`title`、`contentJson`、`tagNames`。
- 标签按名称而不是 ID 保存，使版本恢复不依赖后来被删除的标签记录。
- 新格式恢复标题、正文、标签和重点；旧顶层 Delta 数组只恢复正文并保留当前标题和标签。
- 损坏快照必须解析失败并保持当前笔记不变。

该方案复用原 `snapshot_json TEXT`，不修改表结构；相比拆分多列，兼容旧 Delta 快照的迁移成本更低。

#### 可搜索范围树

- 未输入关键词时只加载顶层书；展开书、章时按需读取直接子节点并缓存。
- 搜索书、章、节名称时补齐祖先路径；共同祖先合并显示，避免重复书和章。
- 输入使用约 250ms 防抖和 generation 隔离，关闭弹窗后销毁搜索词、展开状态、缓存和错误。
- `%`、`_` 和反斜杠按普通字符搜索，不能直接改变 LIKE 语义。

没有引入第三方树组件，也没有每次搜索全量加载所有书章节，以控制状态复杂度和大量数据时的界面体积。

### 4. 历史版本管理增强设计

- `note_version` 增加可空 `name`，数据库 schema v1→v2；旧记录名称为 null，快照和版本号不重写。
- 未命名显示“版本 N”；自定义名称存在时只显示名称和创建时间，不保留版本号副标题。
- 名称 trim 后最长 50 字符，同一笔记内唯一，不同笔记可同名；清空名称恢复默认显示。
- 没有采用独立元数据表，因为会增加关联和同步删除；没有把名称写入 `snapshot_json`，因为重命名不应重写正文快照。
- 管理模式支持多选、全选和批量永久删除；删除后不重新编号，允许删除全部版本。
- 批量删除使用单一事务；不存在 ID 幂等忽略，任何跨笔记 ID 都使整个操作失败。
- 恢复弹窗提供“恢复前将当前内容保存为新版本”复选框，默认取消；当前状态与目标完全一致时不生成重复版本。
- ViewModel 分离列表、管理选择、变更中和操作错误；删除失败保留选择，数据操作成功后的刷新失败不能反向误报操作失败。

### 5. 多级文件夹系统设计

候选方案包括把现有 `subjects.level` 整体后移、建立独立文件夹表、仅保存文本分组名。最终选择独立 `subject_folders` + 书的可空 `folder_id`：

- 原因是现有书/章/节已固定使用 level 0/1/2；整体后移会改变既有数据和搜索语义，文本分组又无法支持无限嵌套与安全移动。
- 文件夹可无限嵌套，只容纳子文件夹和书；笔记继续只能归属书、章、节。
- 既有书升级后保持 `folderId=null`，不自动创建默认文件夹或移动用户数据。
- 文件夹名 trim 后不能为空、最长 50 字符、同级唯一；禁止移动到自身或后代。
- 安全解散在单一事务中把直属子文件夹和书移到上一级，再软删目标文件夹；根文件夹解散后内容进入根目录或未归类书。
- 文件夹搜索范围递归收集后代文件夹，再展开其书、章、节；不存在范围必须提示失效，不能静默扩大为全部搜索。
- 文件夹不进入笔记历史版本；移动目录不得修改正文、标签、重点或历史版本。

### 6. 主页浏览统一与新建入口设计

- 移除重复树形按钮和独立书章节管理入口，`LibraryBrowserView` 成为唯一笔记主页容器。
- 逐级模式每页只显示当前容器直属内容；展开模式在同页显示当前范围的可折叠树，不跳转独立路由。
- “新建内容”统一创建文件夹、书、章、节；右下角 FAB 始终用于新建笔记，文件夹不能作为笔记归属。
- 新建内容弹窗只收集类型和名称，不默认写入当前或全局位置。
- 创建成功后刷新当前位置、根目录和展开树；取消、空名称、重复名称或非法父级不写数据。

原方案曾考虑在弹窗内一次性列出所有合法父位置，但随着书和文件夹增加会变得臃肿，也会复制目录浏览逻辑，因此后续改为主界面层级位置选择。

### 7. 主界面层级位置选择设计

- 根目录、文件夹、书、章、节均可切换逐级/展开模式；切换后保持当前位置。
- 展开范围严格受当前位置限制：文件夹只看其子树，书只看该书，章只看该章，节只看该节和直属笔记。
- 创建内容时，弹窗确认类型与名称后进入主页位置选择模式；只有选择合法目标后才调用仓储。
- 文件夹和书可选根目录或文件夹；章只能选书；节只能选章。
- 新建笔记从当前位置进入选择模式，文件夹只能继续进入，书、章、节可作为最终归属。
- `LibrarySelectionSession` 保存启动位置、允许范围、内容类型、待创建名称、当前位置和启动前浏览模式；取消后恢复原位置和模式。
- 选择模式隐藏搜索、标签、新建内容、浏览切换和 FAB，防止并行启动第二个操作；面包屑不能越过启动范围。
- 当前节点被删除或移动时停止创建并提示重新选择；创建失败保留会话和位置以便重试。

最终采用共享 `LibraryNavigationVm` 和纯 `LibrarySelectionRules`，而不是继续维护全局平铺选择器，从而让浏览与位置选择使用同一目录事实来源。

# 阶段5目录项目移动与排序 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` (recommended) or `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为文件夹、书、章、节、笔记提供统一三点菜单、同类型拖拽排序、跨目录移动与准确插入位置，并让新建内容稳定追加到末尾。

**Architecture:** 继续使用各业务表的 `sortOrder`；给笔记表新增同级顺序字段。Repository 在 Drift 事务内校验完整同级列表并统一重排，UI 通过独立的排序页和两步移动页维护未保存草稿，保存成功后统一刷新逐级与展开浏览。

**Tech Stack:** Flutter 3.44.4、Dart 3.12.2、Riverpod 3.3.2、Drift 2.34.2、SQLite、Flutter Test、Mocktail

## 设计依据与已确认决策

> 本节由原《阶段5：目录项目移动与排序设计》合并而来。设计文档中的执行要求已拆入后续 Task，本节保留实现时不可改变的产品语义、方案取舍和接口边界。

### 背景与目标

现有文件夹、书、章、节和笔记缺少统一的末尾追加与手动排序规则，操作入口也不一致：文件夹使用三点菜单，书使用独立移动图标，章和节显示进入箭头，笔记没有项目菜单。文件夹移动目标未覆盖完整目录树，部分移动完成后还需要重启应用才刷新。

本计划必须形成以下闭环：

1. 五类项目统一使用三点菜单；
2. 五类项目在各自同级、同类型列表内拖拽排序；
3. 五类项目可跨合法父级移动，并选择准确插入位置；
4. 新建项目默认追加到同级同类型末尾；
5. 移动或排序后立即刷新逐级与展开浏览；
6. 保持文件夹—书—章—节—笔记固定层级，不允许任意混排。

### 产品交互决策

- 文件夹菜单：重命名、移动、调整顺序、安全解散。
- 书、章、节菜单：重命名、移动、调整顺序，不提供解散。
- 笔记菜单：重命名、移动、调整顺序。
- 删除书原有独立移动按钮及章、节原有 `>` 图标；项目主体点击仍执行进入、展开或打开。
- 排序页始终加载真实父级下的完整同类型列表，拖拽只修改页面草稿；只有点击保存才写数据库。
- 分类展示固定：文件夹组在书组之前，章/节组在笔记组之前；`sortOrder` 只在“同一父级 + 同一类型”内有意义。
- 移动采用两步流程：先在可搜索、可展开的完整目录树中选择合法父级，再在目标同类型列表中拖拽确定精确位置。
- 目标可与当前父级相同，此时移动流程等价于重新排序；取消、返回或关闭均不得写入数据。
- 目录树按名称搜索，结果保留祖先路径；同名书章节必须用完整路径区分。
- 笔记菜单重命名只更新标题，不创建 `note_version`；编辑器正常保存仍沿用完整历史版本规则。

### 固定层级与移动目标

| 移动对象 | 合法目标父级 | 持久化父级字段 |
|---|---|---|
| 文件夹 | 根目录或任意其他文件夹，排除自身及后代 | `subject_folder.parent_id` |
| 书 | 根目录（未归类书）或任意文件夹 | `subject.folder_id` |
| 章 | 任意文件夹中的任意书 | `subject.parent_id` |
| 节 | 任意书中的任意章 | `subject.parent_id` |
| 笔记 | 任意书、章或节 | `note.subject_id` |

文件夹、书、章移动时完整保留后代和其中笔记，不拆散内部结构。

### 技术方案与取舍

最终沿用现有业务表的顺序字段，并为 `notes` 新增 `sort_order`：

- `subject_folder.sort_order`：同一父文件夹内的文件夹顺序；
- `subject.sort_order`：同一文件夹内的书，或同一 subject 下章/节的顺序；
- `note.sort_order`：同一书、章或节内的笔记顺序。

来源列表和目标列表在同一 Drift 事务内重排为从 0 开始的连续整数，并以 `sort_order → created_at → id` 作为稳定显示顺序。新建时在事务内使用活动同类项目的 `max(sortOrder) + 1`，空列表从 0 开始。

未采用方案：

- **统一位置关系表：** 能支持五类项目完全混排，但会与现有父级字段形成双重事实来源；本项目已经确认分类展示，因此不采用。
- **小数或字符串排名：** 单次更新较少，但长期需要再平衡，迁移和异常排查更复杂；当前本地 SQLite 数据规模适合连续整数事务重排。

### 数据迁移与事务契约

- 数据库 schema 从 v3 升至 v4，只为 `notes` 增加带默认值的 `sort_order`。
- v3→v4 迁移分别按文件夹父级、书的文件夹、章/节父级、笔记 subject 分组，使用旧顺序、创建时间和 ID 生成稳定连续顺序。
- 迁移不得修改名称、正文、标签、重点、历史版本、软删除状态和父子关系。
- `orderedIds` 必须无重复，并与保存时数据库中的完整活动同级列表完全一致；否则整个事务回滚并提示“列表内容已变化，请刷新后重试”。
- 跨父级移动必须在事务内重新读取移动对象、来源列表、目标父级和目标列表，校验目标与索引后同时重排来源和目标。
- `moveNote` 不修改 `updatedAt`，避免目录整理干扰“最近更新”搜索排序。

### 界面与状态边界

- `LibraryItemKind` 和 `LibraryItemAction` 统一定义五类项目及操作，逐级与展开浏览复用同一菜单。
- 排序页接收不可变 `LibraryReorderRequest`，使用项目业务 ID 作为稳定 `ValueKey`。
- 移动页接收不可变 `LibraryMoveRequest`，状态依次为目标加载、选择父级、选择位置、保存及结果。
- 目标树一次读取活动文件夹和 subject 后构建内存索引；搜索只过滤可见节点，保存前仍由 Repository 重新校验数据库。
- 成功后必须失效当前、根目录、来源、目标、展开树和位置选择相关 Provider，不得依赖重启 App。

### 错误与验证边界

- 空名称、非法目标、循环移动、目标已删除、软删除项目、重复或缺失 ID 均拒绝写入。
- 数据库错误不得向 UI 暴露 SQL、表名或堆栈；失败时保留排序或移动草稿，允许重试。
- 保存期间禁用重复提交，取消时不写数据库。
- 必须覆盖真实 v3→v4 迁移、五类追加/排序/移动、非法目标回滚、菜单一致性、两步移动、即时刷新和笔记重命名历史隔离。
- 最终按“定向测试 → 全量测试 → analyze → 代码生成与格式检查 → Debug APK → 代码审查 → 真机”的顺序验证。
