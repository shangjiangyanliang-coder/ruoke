# 阶段5：目录项目移动与排序设计

## 文档状态

- 状态：已确认
- 日期：2026-07-31
- 适用分支：`feature/notes-mvp`
- 前置功能：文件夹系统、逐级/展开浏览、统一新建、笔记历史版本

## 1. 背景与目标

文件夹、书、章、节和笔记的新建位置目前缺少统一的末尾追加规则，项目之间也无法可靠地手动排序。现有操作入口不统一：文件夹使用三点菜单，书使用独立移动图标，章和节显示进入箭头，笔记没有项目菜单；文件夹移动目标也未覆盖完整目录树。

本次改造需要完成以下目标：

1. 文件夹、书、章、节、笔记统一使用右侧三点菜单。
2. 支持五类项目在各自同级、同类型列表内拖拽排序。
3. 支持五类项目跨文件夹、书、章、节移动，并在目标同类列表中选择准确插入位置。
4. 新建项目默认追加到同级同类型列表末尾。
5. 移动或排序保存后立即刷新逐级浏览和展开浏览，不依赖重启应用。
6. 保持固定层级，不允许文件夹、书、章、节、笔记任意混排或产生非法父子关系。

## 2. 已确认的产品决策

### 2.1 菜单与入口

- 文件夹三点菜单：重命名、移动、调整顺序、安全解散。
- 书、章、节三点菜单：重命名、移动、调整顺序，不提供解散。
- 笔记三点菜单：重命名、移动、调整顺序。
- 删除书原有的独立移动按钮。
- 删除章、节右侧原有的 `>` 图标。
- 点击项目主体仍执行原来的进入、展开或打开笔记行为；点击三点按钮只打开操作菜单。
- 从任意项目选择“调整顺序”后，进入该项目真实父级下的同类型排序页。
- 排序页提供“保存”和“取消”。拖拽只修改页面草稿，保存前不写数据库。

### 2.2 分类展示

不同类型保持分组展示，不支持完全混排：

- 文件夹页面中，子文件夹组显示在书组之前；两个组分别排序。
- 书或章页面中，下级章/节组显示在笔记组之前；两个组分别排序。
- 同一 `sortOrder` 只在“同一父级 + 同一类型”范围内有意义。

### 2.3 移动规则

移动采用两步流程：

1. 在可搜索、可展开的完整目录树中选择合法目标父级。
2. 在目标父级的同类型列表中拖拽待移动项目，确定准确插入位置后保存。

合法目标如下：

| 移动对象 | 合法目标父级 | 父级字段 |
|---|---|---|
| 文件夹 | 根目录或任意其他文件夹；排除自身及其后代 | `subject_folder.parent_id` |
| 书 | 根目录（未归类书）或任意文件夹 | `subject.folder_id` |
| 章 | 任意文件夹中的任意书 | `subject.parent_id` |
| 节 | 任意书中的任意章 | `subject.parent_id` |
| 笔记 | 任意书、章或节 | `note.subject_id` |

补充规则：

- 文件夹、书、章移动时，其完整后代和所含笔记整体保留，不拆散内部结构。
- 目标父级可以是当前父级；此时第二步只调整当前顺序。
- 取消、返回或关闭流程时不写入数据。
- 目录树按名称搜索；搜索结果保留祖先路径，书和章仍可展开，以区分同名节点。

### 2.4 笔记重命名

- 从笔记三点菜单执行“重命名”时，只修改当前笔记标题。
- 此操作不创建 `note_version` 历史快照。
- 从编辑器正常保存标题、正文或标签时，继续使用现有历史版本规则。
- 旧历史版本仍保留其快照中的标题；恢复旧版本时可按既有逻辑恢复该标题。

## 3. 技术方案决策

### 3.1 采用方案

沿用每张业务表的 `sortOrder`：

- `subject_folder.sort_order`：文件夹在同一父文件夹中的顺序。
- `subject.sort_order`：书在同一文件夹中的顺序，或章/节在同一父 subject 中的顺序。
- `note.sort_order`：笔记在同一书、章或节中的顺序，本次新增。

移动和排序保存时，将来源列表与目标列表整理成从 0 开始的连续整数序号。所有相关更新在同一个 Drift 事务中完成。

### 3.2 未采用方案

#### 统一位置关系表

优点是可以支持文件夹、书、章节、笔记完全混排；缺点是会重复现有父子字段，引入双重事实来源。本次已确认分类展示，因此不采用。

#### 小数或字符串排名

优点是多数拖拽只需要更新一个项目；缺点是长期使用需要重新平衡排名值，异常排查和数据迁移更复杂。当前为本地 SQLite、小规模目录，批量写入连续整数更简单可靠，因此不采用。

## 4. 数据结构与迁移

### 4.1 Schema 变更

数据库 `schemaVersion` 从 3 升至 4。

`Notes` 表新增：

```dart
/// 同一书、章或节内的显示顺序。
IntColumn get sortOrder => integer().withDefault(const Constant(0))();
```

`Note` 领域模型同步增加：

```dart
final int sortOrder;
```

Drift 生成文件通过 `build_runner` 重新生成，不手工修改生成代码。

### 4.2 旧数据迁移

升级事务按以下规则生成稳定、连续的顺序：

1. 文件夹按 `parent_id` 分组，以 `sort_order ASC, created_at ASC, id ASC` 排序后写入 `0..n-1`。
2. 书按 `folder_id` 分组，以同样规则整理；`folder_id IS NULL` 是独立分组。
3. 章、节按 `parent_id` 分组，以同样规则整理。
4. 笔记按 `subject_id` 分组，以 `created_at ASC, id ASC` 排序后写入 `0..n-1`。

迁移不修改名称、正文、标签、重点、历史版本、软删除状态和父子关系。测试需要从真实 v3 表结构创建旧库并升级，不能只在 v4 内存库中模拟。

### 4.3 稳定排序

所有目录浏览查询使用以下兜底顺序：

```text
sort_order ASC → created_at ASC → id ASC
```

即使旧数据、导入数据或异常中断造成重复 `sortOrder`，显示结果仍保持稳定。

搜索页面继续使用用户选择的标题或更新时间排序，不使用目录手动顺序。

### 4.4 新建默认位置

新建项目时，在写入事务内读取同父级同类型活动项目的最大 `sortOrder`：

```text
newSortOrder = maxSortOrder + 1
```

空列表从 0 开始。软删除项目不参与最大值计算。

## 5. Repository 接口契约

接口继续统一返回 `Future<Result<T>>`，验证错误使用 `ValidationException`，数据库错误使用不泄漏 SQL 的 `DatabaseException`。

### 5.1 FolderRepository

```dart
Future<Result<void>> moveFolder({
  required String folderId,
  required String? newParentId,
  required int targetIndex,
});

Future<Result<void>> moveBook({
  required String bookId,
  required String? folderId,
  required int targetIndex,
});

Future<Result<void>> reorderFolders({
  required String? parentId,
  required List<String> orderedIds,
});

Future<Result<void>> reorderBooks({
  required String? folderId,
  required List<String> orderedIds,
});
```

现有移动接口增加目标索引，调用方必须明确最终位置。安全解散文件夹时，直属子文件夹和书分别追加到上级对应分组末尾，然后整理序号。

### 5.2 SubjectRepository

```dart
Future<Result<void>> rename({
  required String id,
  required String name,
});

Future<Result<void>> moveSubject({
  required String subjectId,
  required String newParentId,
  required int targetIndex,
});

Future<Result<void>> reorderChildren({
  required String parentId,
  required List<String> orderedIds,
});
```

`moveSubject` 只处理章和节：

- 章必须移动到书，目标 `level == 0`。
- 节必须移动到章，目标 `level == 1`。
- 目标层级必须恰好比移动对象低一级。
- 书的文件夹移动仍由 `FolderRepository.moveBook` 处理。

### 5.3 NoteRepository

```dart
Future<Result<List<Note>>> listBySubject(String subjectId);

Future<Result<void>> renameTitle({
  required String id,
  required String title,
});

Future<Result<void>> moveNote({
  required String noteId,
  required String subjectId,
  required int targetIndex,
});

Future<Result<void>> reorderNotes({
  required String subjectId,
  required List<String> orderedIds,
});
```

`renameTitle` 只更新标题和 `updatedAt`，不调用现有会写历史快照的 `update`。`moveNote` 只更新归属与目录顺序，不修改 `updatedAt`，避免位置整理干扰“最近更新”搜索排序。

### 5.4 重排提交约束

`orderedIds` 必须满足：

- 无重复 ID；
- 与数据库中该父级、该类型的全部活动项目完全一致；
- 不包含软删除或其他父级项目；
- 保存时重新读取数据库校验，不能只相信页面草稿。

不满足条件时整个事务回滚并返回“列表内容已变化，请刷新后重试”。

## 6. DAO 与事务规则

DAO 提供小而明确的原语：

- 查询同父级同类型项目，稳定排序；
- 查询最大 `sortOrder`；
- 更新单项父级和 `sortOrder`；
- 按 ID 更新单项 `sortOrder`；
- 更新名称；
- 校验活动项目和目标。

Repository 负责业务规则、完整列表校验和事务边界。DAO 不直接向 ViewModel 暴露。

跨父级移动的事务顺序：

1. 重新读取移动对象、来源同类列表、目标父级和目标同类列表。
2. 校验层级、循环关系、目标存在性和目标索引范围。
3. 从来源列表移除对象。
4. 若来源和目标相同，直接在同一列表按目标索引重新插入。
5. 若跨父级，更新对象父级字段，并插入目标列表。
6. 来源和目标列表分别写入连续 `sortOrder`。
7. 任一步失败则回滚全部变更。

## 7. 界面与状态架构

### 7.1 统一项目菜单

新增可复用的项目操作菜单组件，以项目类型决定可见操作：

```dart
enum LibraryItemKind { folder, book, chapter, section, note }

enum LibraryItemAction { rename, move, reorder, dissolve }
```

`LibraryBrowserView` 与 `LibraryExpandedTree` 复用同一菜单，避免逐级模式和展开模式出现不同操作。

### 7.2 排序页

排序页接收不可变请求：

```dart
class LibraryReorderRequest {
  final LibraryItemKind kind;
  final String? parentId;
  final String title;
}
```

页面加载同父级同类型活动项目并保存 ID 列表副本。使用 Flutter 3.44.4 的 `ReorderableListView`/`onReorderItem`，每一行使用项目 ID 构造稳定 `ValueKey`，并显示明确拖拽把手。

从某个项目的“调整顺序”进入时，排序的是完整同级同类型列表，不只操作被点击的一项。

### 7.3 移动页

移动页接收：

```dart
class LibraryMoveRequest {
  final LibraryItemKind kind;
  final String itemId;
  final String itemName;
}
```

流程状态分为：

```text
loadingTargets → choosingParent → choosingPosition → saving → success/error
```

目标树一次加载全部活动文件夹和 subject，在内存中构建父子索引。搜索时只改变可见节点集合，不重新请求数据库。选择父级后重新读取目标同类列表，待移动项目以特殊样式插入并允许拖拽。

最终保存前由 Repository 再次校验数据库当前状态。页面缓存只负责交互，不作为数据真实性依据。

### 7.4 页面刷新

操作成功后统一失效：

- 当前 `libraryBrowserProvider(location)`；
- 根目录和相关来源、目标位置的 `libraryBrowserProvider`；
- 展开树数据 Provider；
- 位置选择规则 Provider。

来源页中的项目应立即消失或改变顺序，目标页下次打开时直接显示新位置。不得通过重启 App 触发刷新。

## 8. 错误处理

- 空名称：不允许保存。
- 文件夹移动到自身或后代：拒绝。
- 书、章、节、笔记目标类型错误：拒绝。
- 移动对象或目标已删除：提示“项目或目标位置已不存在，请刷新后重试”。
- 排序提交 ID 缺失、重复或归属不一致：提示“列表内容已变化，请刷新后重试”。
- 数据库事务失败：保留排序/移动页面草稿，允许重试或取消。
- 保存过程中禁用返回提交和重复点击，避免并发写入。
- UI 不展示 SQL、表名、堆栈等内部细节；技术细节仅保留在 `DatabaseException.techDetail`。

## 10. 外部参考与兼容性

- Flutter 官方 `ReorderableListView` 要求所有列表项具有稳定 key；Flutter 3.44.4 使用 `onReorderItem`，该回调已提供移除旧项后的目标索引。
- Drift 官方迁移文档要求新增非空列时提供默认值或使用 `TableMigration` 转换旧行；本项目列本身默认 0，再在升级事务中按分组回填连续序号。
- Drift 官方事务用于保证多行更新的原子性；移动、排序和迁移都必须在事务中执行。
- 本次不新增第三方拖拽、树形或排名依赖，优先使用 Flutter 和 Drift 现有能力。
